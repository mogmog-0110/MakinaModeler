# AI からの編集（Phase 7・コア側）

**状態**: `makina-core` 側は動作確認済み。ブリッジ（CEF）は Phase 3 待ち。

---

## 1. 何が主張なのか

「AI が使っていて強い」の中身は、**エージェントが自分の仕事を数値で確かめられること**である。

絵しか見られないエージェントは、動かしたボスがボアを避けているかを**推測**するしかない。
`measure` を叩けるエージェントは**数字**を得る。この差が、
「AI に触らせられるツール」と「AI が触れるだけのツール」を分ける。

もう一つは**巻き戻しが正確である**こと。
`Scene` は 1 個の trivially-copyable な struct なので、スナップショットはコピーそのものである。
コマンドに逆操作を持たせる必要が無く、**「逆操作が微妙に間違っている」という事故が原理的に起きない**。
試す → 見る → 戻す、が厳密に成立する。

## 2. 3 つの動詞

```
makina_edit describe <scene.json>                    ツリー（id と名前付きパラメータ）
makina_edit apply    <scene.json> <commands.json> -o <out.json>
makina_edit measure  <scene.json>                    隙間・干渉・浮き・対称性
```

ヘッドレス。GPU もウィンドウも要らない。

### 2.1 `describe`

出力は**シーンファイルそのものと同じ語彙**である（`SceneJson` の出力に `summary` を足しただけ）。
エージェントが読む名前と、ファイルに書く名前と、エラーに出る名前が全部同じ。

```json
{
  "root": { "op": "SceneRoot", "id": 1, "children": [
      { "op": "Box", "id": 2, "name": "Box", "x1": -0.5, "x2": 0.5, ... } ] },
  "summary": { "nodes": 2, "materials": 1, "unsupported": 0, "nextId": 3,
               "bounds": { "min": [...], "max": [...] } }
}
```

### 2.2 `apply`

```json
[
  {"op":"add","parent":1,"node":{"op":"Difference","name":"bored plate"}},
  {"op":"add","parent":3,"node":{"op":"Cylinder","name":"body","capPoint":0.25,"basePoint":-0.25,"radius":1.2}},
  {"op":"add","parent":3,"node":{"op":"Cylinder","name":"bore","capPoint":1.0,"basePoint":-1.0,"radius":0.45}},
  {"op":"remove","id":2}
]
```

| コマンド | 引数 |
|---|---|
| `add` | `parent`（id）・`node`・`at`（省略で末尾） |
| `remove` | `id`（配下ごと） |
| `move` | `id`・`parent`・`at` |
| `set` | `id` + 名前付きパラメータ |
| `rename` | `id`・`name` |
| `material` | `id`・`material` |
| `undo` / `redo` | — |

パラメータは `{"radius": 0.7}` と書く。`params[2]` ではない。
**`params[2]` は保管形式の話であって、モデルの話ではない。**
対応表は `Op.hpp` の 1 箇所にしかなく、シーンファイルもコマンドもエラーもそこを見ている。

### 2.3 `measure`

ルート直下の部品どうしの隙間・干渉、浮いている部品、3 軸の対称性を返す。
ペアは**先頭 8 部品まで**。gap 1 本が数千回の SDF 評価なので、
30 部品なら 435 ペア＝エージェントがシェルの前で待つことになる。打ち切ったら `note` に書く。

## 3. 設計で外せなかった 2 点

### 3.1 途中で止まる。半端に適用しない

コマンドが 1 つ失敗したら**そこで止める**。
続行すると、エージェントは「5 個中 3 個だけ適用された木」に対して次の推論を始める。
実際に起きた例：

```
{"index":0, "ok":true,  "message":"added id 3"}
{"index":1, "ok":false, "message":"no node with id 4"}
```

新ノードの id を 4 だと決めつけたバッチ。1 個目は通り、2 個目で止まり、
シーンは**1 個目まで適用された状態**で残る。エージェントは `describe` で見て組み直せばよい。

### 3.2 知らないキーは黙って無視しない

```
op 'Cylinder' has no parameter 'radius2'; it takes capPoint, basePoint, radius
```

無視すると、エージェントは「編集した」と信じて、変わっていない絵から推論を続ける。
**沈黙するより失敗する方が安全**である。エラーには必ず**受け付けるキーの一覧**を入れる。

## 4. 編集はツリーを作り直す（`Edit.hpp`）

`firstChild` / `childCount` は**兄弟が隣接している間しか成立しない**。
挿入や削除は以降の index を全部ずらすので、その場で直そうとすると
`parent` / `firstChild` / `childCount` を全域で整合させることになり、
1 つ間違えると**親が 2 つあるノード**ができる。

なので編集は毎回**作り直す**。ローダと同じ「子ブロックを先に確保してから再帰する」walk を使う。
`Scene` は flat POD なので、作り直しは高々 `kMaxNodes` 件の走査＋固定配列 2 本のコピーで、
どうせ履歴が取るコピーと同じものである。

**ノードは index ではなく id で指す。** index は現在のレイアウトについての事実で、
何か挿入した瞬間に嘘になる。id は一度配って二度と使い回さない（CSG_NODE.md 6.3）。

### 実際に踏んだバグ

最初の実装は `to.nodes[dst] = from.nodes[src]` で丸ごとコピーしていた。
これは**直前に書き込んだ `parent` を、旧レイアウトの index で上書きする**。
`edit_check` の「node N has two parents」で 276 件落ちて発覚した。
コピー前に `parent` を退避して書き戻す 2 行で直っている。

## 5. 検証

| テスト | 内容 |
|---|---|
| `edit_check` | 全 12 シーンで、編集ごとにツリー不変条件（隣接・親の一致・二重親なし・id 一意・親が子より前）を検査。**add → remove で距離場が完全に戻ること**、履歴の undo がバイト単位で戻ること。7,784 件 |
| `command_check` | 受理と**拒否**。誤字パラメータ・未知の op・未知のコマンドが拒否され、かつ**シーンが変わっていない**こと。バッチが最初の失敗で止まること。208 件 |

> **拒否側を同じ数だけ検査している**のは、このコマンド層の失敗モードが
> 「間違った編集をする」ではなく「**何もせずに成功したふりをする**」だからである。

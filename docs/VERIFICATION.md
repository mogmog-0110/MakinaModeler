# 何をどう確かめているか

**このプロジェクトで一番強い主張は「速い」でも「きれい」でもなく、
**独立に書かれた実装どうしが一致する**ことである。**
自分で書いた 2 つが一致しても、同じ勘違いを共有しているだけかもしれない。

だからこの文書は「テストがある」ではなく **どの軸が何を捕まえ、何を捕まえないか** を書く。

---

## 7 つの照合軸

**規模はすべて 2026-08-14 に走らせた実測値である。** 書き写した数字は放っておくと腐るので、日付を付けてある（性能値でそれをやらずに 4 日放置した — 下の節）。

| 軸 | 何と何 | 規模 | 捕まえるもの |
|---|---|---|---|
| 1 | 移植 ↔ Grasp3D（Java） | 82,985 標本 + 501 + 7,812 件 | 距離場・計測・POV 出力の移植ミス |
| 2 | 距離場 ↔ 境界表現（BSP） | 156,932 サンプル | ブーリアンの解釈違い |
| 3 | 距離場 ↔ POV-Ray（**輪郭**） | IoU 0.9949〜0.9996 | 幾何・変換・カメラ・左右の向き |
| 4 | 距離場 ↔ POV-Ray（**画素**） | 平均差 0.14〜4.76 | 陰影・マテリアル・パターン・光・影・カメラ種別・透過 |
| 5 | 書き出したメッシュ ↔ 距離場 | 最悪 0.0188（許容 0.0762） | 出口の表現が中身とずれていないか |
| 6 | 生成シェーダ ↔ インタプリタ | 11 シーンで **差 0** | 同じ規則の 2 実装が離れていないか |
| 7 | 経年変化パス ↔ **シーンそのもの** | 同じ形・alpha 違いの 2 枚 | 機能が絵に届かなくなっていないか |

加えて **POV の往復**（エクスポート → 読み戻し）が全 12 フィクスチャで
**幾何 0.00e+00・外観 0.00e+00**。外観は 1,331 点それぞれで「そこを塗るのは何か」を
評価器の選択規則どおりに引き、GPU が受け取る 46 個の float を全部突き合わせている。

> **軸 3 と 4 は別物である。** 輪郭はジオメトリだけを見るので、
> **2 つのレンダラが全ての輪郭で一致し、全てのマテリアルで食い違う**ことがありうる。
> 軸 4 はそれを塞ぐために、POV の `finish{}` と `pigment` を**こちらが POV に合わせて**実装して初めて成立した。

## 軸 4 が実際に見つけたもの

比較器（`spike/src/color_compare.cpp`）は作った初回に 2 件を出した。どちらも
**目では分からず、数字にすると一目**という種類である。

**ブーリアン節点のマテリアルがエクスポートされていなかった。**
Grasp3D のファイルはマテリアルを必ずプリミティブに置くので今まで表に出なかった。
レンダラは祖先を辿って解決するので**塗っていて、.pov は塗っていなかった** —
POV 側にチェッカーの箱が丸ごと存在しなかった。平均差 55.4 → 7.7。

**POV のスペキュラは指数ではなくガウシアンだった。**
`exp(-(acos(N·H)/roughness)²)`。Blinn-Phong の指数に変換していたので、
roughness 0.6875 では**ほぼ平坦**になり全画素が持ち上がる。
暗いチェッカーが 100、POV は 76 で、**片方の色だけ一律に**ずれていた。平均差 4.7、penrose は 8.6 → 4.2。

fisheye も初回 mean 95 で外れた。**POV は right/up ベクトルの長さで正規化する**ので、
アスペクトを掛けると「見た目の丸い」絵になり全画素で食い違う。

**透過は 2 つの取り違えが重なっていた。** どちらも「係数を当てて通す」ではなく、
**POV に係数そのものを吐かせて**割った。`finish{ambient 1 diffuse 0}` の球は
画素にピグメントの色 × 係数がそのまま出るので、フィルタと色を振れば係数が読める。

**1つ目 — 減衰は `1 − filter` ではない。** POV は **`1 − filter × ピグメントの最大チャンネル`**
で減衰させる。白では両者が一致するので、色を付けて初めて分かれる。
実測 0.4117 / 0.4115 / 0.4117 に対し `1 − 0.75 × 0.784 = 0.4118`、
filter 0.25 と 0.5 でも小数 4 桁まで合う。
透過側の色付けが `filter × ピグメント` であることも、板を後ろに置いて
**球の表と裏の 2 層**として計算した値（0.3743/0.6513/0.4242）が
実測（0.3763/0.6514/0.4233）に一致することで裏が取れた。

**2つ目 — 距離場の勾配は必ず外を向く。** 透過体の裏の壁は内側から当たるので、
法線が視線から背を向けたまま照明され、影の中にあるかのように落ちていた。
**POV に裏面という概念は無く、見ている側へ法線を倒す**（POV の平面が両側から照らされるのと同じ理由）。

この 2 つで glass は 14.90 → 2.43。さらに**輪郭ぎわだけ**が残ったので見に行くと、
内側は階調まで一致しているのに外周 1〜3 画素で 134 対 66 だった。
擦れる角度では面を離れる一歩が閾値の内側に収まってしまい、
**同じ面が層の数だけ自分の上に重なっていた**。閾値を抜けるまで進めるようにして
glass **0.27**、ペットボトル（アルファ 0.1 の殻が何重にもある）**4.02**。

層の上限は POV の `max_trace_level` と同じ 5 にしてある。16 まで上げても平均は動かなかったので、
**深さではなく式の問題だった**ことがここでも確かめられている。

**屈折を入れたら、屈折とは関係のないバグが出てきた。** `interior{ior 1.5}` の球を
チェッカーの壁の前に置くと平均 114 — ほぼ無関係な 2 枚である。
中を見ると食い違っていたのは**球の外側の壁**で、マス目がまるごと 1 つずれていた。
壁を `Translate` で動かしていたのが原因で、**書き出した .pov では POV がパターンを壁ごと動かすのに、
こちらは世界座標でパターンを引いている**。動かさず同じ場所へ置き直すと 114 → **0.50**。

既存の `pigment` フィクスチャがこれを捕まえなかったのは、
**そこでテクスチャ付きの立体を一度も動かしていない**からである。
「軸が 5 本ある」ことと「その 5 本が使われている」ことは別だという例になった。

**直したときに、正しい規則を決めたのは好みではなくファイルだった。** 素直に考えると
「パターンは物体と一緒に動く」だが、`pigment` フィクスチャはそれで 4.76 → 21.26 に悪化した。
書き出した .pov を読むと理由が出ている — エクスポータは**変換を葉のプリミティブまで押し下げる**ので、
ブーリアンに付いた `pigment` の後には変換が 1 つも無く、POV はそれを世界座標で読む。
プリミティブに付いたものは直後の `translate` で動く。**同じ分岐を平坦化に入れたら両方通った** —
pigment 2.83、refraction 0.50。

そのうえで**わざと戻して落ちるのを確かめた**：規則を消すと pigment 14.87 / refraction 114.27 で
両方落ちる。フィクスチャがこの経路を本当に通っていることの担保である。

**そしてインポータは `filter` を落としていた。** 屈折のためにインポータへ
「往復して同じ値が返るか」を足したところ、`rgbf<1,1,1,0.5>` が不透明として戻ってきた。
4 番目の成分を読んだうえで捨てていたのである。**ガラスのシーンを読むと、ガラスが消える。**

往復の照合が **0.00e+00** を出し続けていたのにこれを見逃していたのは、
**その照合が幾何しか比べていない**からだった。節点数と距離場だけを見ていて、
マテリアルは一度も突き合わせていなかった。
「往復が完全一致」という言葉が、何と何の一致なのかを書いていなかったのが実際の穴である。

## 外観の往復を軸にしたら、3 件出てきた

穴を名前で書いて放置するのは直さないのと同じなので、**外観そのものを軸にした**。
節点ごとではなく**評価器が選ぶもの**を比べる — `Difference` の刃は POV 側で本体の
マテリアルに差し替わるが、評価器はその面のマテリアルを読まないので、節点で比べると
**どちらのレンダラも見ない値**について不一致を報告してしまう。
そこで距離場と同じ 1,331 点で「そこを塗るのは何か」を引き、GPU に渡る float を全部比べる。

入れた瞬間に 12 フィクスチャ中 7 つが落ちた。

**1. 色が丸ごと消えていた。** 素の `pigment{}` と `finish{}` は 1 つのテクスチャの項目なのに、
ブロックごとにマテリアルを作り直していた。エクスポータはまさにその順で書くので、
**書き出した .pov を読み戻すと全シーンが白になっていた**。

**2. パターンを一切読んでいなかった。** `checker` / `gradient` / `radial` と `color_map` は
書けるが読めない、という片側だけの実装だった。読めるようにした（回転だけは `Pigment` に
置き場が無いので名前を挙げて断る）。

**3. マテリアルを変換ノードに付けていた。** POV はテクスチャを図形の中に、`translate` を
その後に書く。読み戻しでは変換のラッパー側に付いていたので、R-15 の規則で
パターンが世界座標扱いになり、チェッカーが 1 マスずれた。図形側に付けるよう直した。

いずれも**絵が出てしまう**種類の欠落である。エクスポートしか使っていなければ誰も気付かない。

**光源も同じ形をしていた** — `light_source` は書けるのに読めず、読み戻すと真っ暗になる。
読めるようにして往復に足した（3 シーン、差 0.00e+00）。
POV に置き換えのない 2 つ、**指向性光源**（POV に無いので 1 万単位先の点光源として書いており、
ファイルからは遠い点光源と区別がつかない）と **softness**（POV の点光源は硬い影しか作らない）は、
「比べない」と**理由つきで印字する**。

**そして光源の負の対照が、最初は落ちなかった。** `directional` と `shadowless` は `uint32` で、
float として読むと値 1 が 1e-45 付近の非正規化数になる — **どんな閾値より小さい**。
フラグを潰しても検査が通ってしまうので、整数として名指しで比べるように書き直した。
`Light` を uint8 で持っていた頃の失敗（HLSL に uint8 が無く、以降の全フィールドがずれた）と
同じ場所に、同じ理由で二度目の穴が空いていたことになる。

## 指標を 2 度作り直した

**どちらも「閾値を選べば通る」に逃げなかった結果である。**

**パーセンタイルは硬い縁のパターンで機能しない。**
チェッカーのマス境界では 2 色が 200 階調離れているので、
面の位置が半画素ずれる（片方はマーチ、片方は求解なので必ずずれる）だけで
その画素に 200 が入る。平均 4.7・パターンは完全に一致しているシーンで p99 が 41 になった。
→ **「強く違う画素の割合」**に変えた。

**メッシュの照合は三角形自身の辺長で測ってはいけない。**
24 分割のトーラスを引くと、**削り残る量はトーラス側の分割**で決まるのに
残るスライバは極小なので比が 113 倍に跳ねる。
`hero_flange` の最悪点は場の外 0.0087 で、`1.15 × (1 − cos(π/24)) = 0.0099` に一致した。
**誤差は「削られる面」ではなく「削る面」に属する。** → シーン半径を尺度にした。

## 照合しないと決めたもの

**近似して「読めた／描けた」ことにするのが、この設計で最悪の失敗形である。**
落ちてくれないので誰も気付かない。

| 対象 | 理由 |
|---|---|
| POV のノイズ系 pigment（marble / bozo …） | POV 独自の置換表なしでは「似た何か」にしかならず、照合できない |
| `sor` / `blob` / `isosurface` など | このモデルに対応する形が無い。円錐の積み重ねで近似すると別の立体になる |
| `rand` / `seed` | POV の乱数そのものを再現しない限り一致を主張できない |
| `panoramic` カメラ（**正方形でないフレーム**） | 横が「角度そのもの」でも「それをアスペクトで割ったもの」でもない。中央付近では割る式に一致し、縁で 76% 離れる。表はあるが式が無いので、正方形の場合だけ照合する |
| 無限平面（軸 3・5） | 半空間はソリッド形を持たない。有限の代用が尽きたところで必ず食い違う |

いずれも**名前を挙げて断る**。`makina_povin` は読めなかった構文を行番号つきで報告し、
`CsgBake` は焼いた .cso がそのシーンから焼かれたものかをハッシュで照合する。

## `panoramic` — 2 度外して、3 度目は当てずに測った

**同じ式を 3 通り試すのは当てにいくのと同じである。** 過去 2 回は 159 と 95（限度 6）で、
どの部分が違うのかを言えなかった。そこで式を考えるのをやめ、**写像そのものを測った** —
既知の方向に光る球を 1 つ置き、それが落ちる画素を読む。

正方形のフィルムで、答えは 2 行だった。

```
ndc.x = -ヨー / 90 度        ndc.y = -仰角 / 90 度
```

厳密に線形（仰角 10 度 → 0.1111、40 度 → 0.4444）で、しかも **`angle` は完全に無視される**
（60 / 90 / 180 で同一の絵）。過去 2 回の失敗はこの 2 点そのものだった —
**POV が見ていない `angle` で割り**、**角度そのものである縦を tan にしていた**。
入れ替えると平均 3.81 で通り、旧式に戻すと 28.40 で落ちる。

計測器は先に**答えの分かっている場所で確かめた**。`perspective` に対して
このプローブは `tan(ヨー)/tan(angle/2)` を小数 3 桁まで再現する。
それが合わなければ、`panoramic` の数字は式ではなく測り方の話だった。

**正方形でないフレームは分かっていない。** 横は中央付近ではアスペクトで割る式に一致し、
縁では 76% 離れる。表は取れているが式が無いので、そこは照合しない。

## 「比較している」と書いてあって、していなかった

シーンを評価する経路は 2 つある。生成シェーダは計画を直線コードに展開して**コンパイル**し、
インタプリタは同じ計画をバッファから明示スタックで**歩く**（モデルを変えても何もコンパイルせずに
済むので、エンジン側がこちらを使う）。**同じ規則の 2 実装**であり、このプロジェクトが
一番警戒している形そのものである。

`scene_interpret.hlsl` には「両者の絵を比較している」と書いてあった。**していなかった。**
`--interpret` で描くことはできたが、それを突き合わせる場所がどこにも無かった。
今日そこへ 2 つとも同じチャンネル（ピグメント番号）を足したので、実際に効く穴だった。

`interpret-check.bat` を足した。限度は平均 0.5（POV との照合は 6）— **別のレンダラではなく、
同じ陰影を同じ計画に対して走らせる 2 経路**なので、演算順序しか違わない。
11 シーンすべてで **差 0.00、1 画素も違わない**。限度を緩く取って通したのではない。

負の対照も取ってある。インタプリタ側だけピグメント番号を落とすと、
`pigment` が平均 75.15、`refraction` が 65.07 で落ちる。

## 束縛されていて、何もしないキー

同じ問いをアプリ側にも向けた — **「この操作は実装されている」と書いてあるものは、本当に実装されているか。**

`Keymap.hpp` の一覧には「このビルドが実行できる操作」と書いてあり、
読み込んだキーマップをそれと照合して、綴り違いをキーが効かなくなる前に弾いている。
**その一覧が正しい間しか成立しない。** 正しくなかった：

- **`select.add`**（Shift + クリック）は一覧にあり、両プリセットが束縛していて、
  ビューポートは一度も名前を出していなかった。つまり Shift + クリックは**何も起きない** —
  素の選択すら走らない（イベントはどの枝も拾わない操作名に解決されるので）。
- **`snap.hold`** は `CONTROL` に束縛されているのに、ビューポートは `in.ctrl` を直接読んでいた。
  束縛は飾りで、キーマップで別のキーに移しても何も変わらない。

`snap.hold` はキーマップ経由に直した（修飾キー以外に束縛したら起動時に断る）。
`select.add` は多選択という**機能**であって直しではないので、
**約束の側を実態に合わせた** — 一覧と両プリセットから外し、多選択と一緒に戻すと書いた。
実装していない操作を束縛したままにしない、という方針である。

そして次の 1 件を防ぐために `keymap_audit` を足した。
一覧のすべての操作名が、**コメントを除いた**ビューポートの本文に現れることを確かめる。
証明できるのは「名前がコードに届いている」ことまでで、それ以上ではない — と道具自身に書いてある。
枝が名前を出しつつ何もしない場合は捕まえられないが、そちらは `viewport-check.bat` が
キーを流してツリーを比べる側の担当である。

`select.add` を一覧に戻すと落ちることも確認した。

**そして監査は片方向しか見ていなかった。** 「一覧の操作がビューポートに届くか」は見ていたが、
「一覧の操作が**押せるか**」は見ていない。`select.clear` がまさにそれで、
一覧にあり、ビューポートが処理していて、**どちらのプリセットも何にも束縛していなかった** —
押す手段が存在しない。ミュートの検査を書こうとして選択を解除できず、そこで気付いた。

**そして 3 つ目の向きがあった。** ビューポートが持つ編集を、コマンド層も持っているか。
これは 2 度破れていた — ミュートはキーだけで、**移動・回転・拡縮はそもそもコマンドが無かった**
（コマンド層の `move` は親子の付け替えである）。**どちらも手で見つけた。** それは約束の守り方ではない。

そこで `Keymap.hpp` に `editCommands()` を置き、`edit.` の操作とそれを行うコマンドの対応を
**宣言させる**ことにした。監査は 2 つを確かめる — 対応の無い `edit.` 操作があれば落ち、
名指しされたコマンドをコマンド層が捌いていなければ落ちる。
ビューポートに編集を足すことは、それを行うコマンドの名前を言うことになった。
「まだ無い」という答えはビルドが受け付けない。両方の壊し方で落ちることは確認した。

両方向を見るようにしたが、**「両プリセットに必須」は厳しすぎる**。
Maya には正面/右/上や平行投影のキーが無く、プラン 3.A の表も Maya 欄を「—」にしている。
そこで規則は「**どちらか一方が束縛していること**」— これで `select.clear` は捕まり、
Maya に存在しないキーを発明させることにはならない。

そのうえで**多選択そのものを実装し**、`select.add` を正規に戻した（27 操作、全部が届く）。
規則は 1 つだけ — **編集は「他の選択に含まれていない選択」にだけ届く**。
ビューポート検査に 4 件足してある（2 つ動かす・2 つ消す・2 つ複製する・親と子を一緒に消す）。

**この 4 件は、書いた直後に 2 回間違っていた。**
1 つ目は cmd が `13,15` をカンマで 2 引数に割っていて、選択が 1 つしか渡っていなかった
（検査は通っていたが、通していたのは単一選択の経路である）。
2 つ目は、保存された JSON がマテリアルも `{"id": N}` で書くので、
**ノード 4 が消えてもマテリアル 4 が一致して「まだ居る」と読めていた**。
id を 5 より大きいものに選び直した。どちらも「検査が何を見ているか」の間違いで、
実装のバグより見つけにくい種類である。

規則の負の対照も取った。`topLevel` を外すと `nested` が落ち、ログには
`refused: no node with id 14` が出る — 親を消した時点で子は消えているので 2 件目が拒否され、
ジェスチャ全体が破棄されて木が無傷のまま残る。それがこの規則の防いでいる失敗である。

## 全部の軸が通っても、何も確かめていないことがある

ミュートを入れたとき、旗を解釈するのは `withoutMuted` **一箇所だけ**という設計にした。
そのうえで、ミュート入りのフィクスチャを 1 本足して 6 軸すべてに流した。全部通った。

**それは一致の証明であって、旗が効いている証明ではない。** 全経路が揃って無視していても、
やはり全部一致する。実際そのとき、旗を見ていたのはビューポートだけで、
オフスクリーン描画・焼き込み・メッシュ書き出しは**全員そろって無視**していた。
だから軸は何も言わなかった。

3 つの入口に「固体を渡す」規約を通し、POV 往復も**固体どうしで**比べるようにした
（.pov には「この節点はミュート」と書く手段が無いので、往復が保てるのは残った形だけである）。
そして**フィクスチャ自体を検査する**ようにした — 旗を持つシーンは、旗によって
節点数と境界が実際に変わっていなければならない。

**その検査も、最初の版は落ちなかった。** 旗を消すと `hasMuted` が偽になり、
そのシーンは検査対象から**静かに外れる**だけだったからである。
「旗を持つシーンが少なくとも 1 本あること」を足して、ようやく落ちるようになった。
**「検査を書いた」と「検査が効いている」は別だ**という、この文書で 3 度目の例になる。

## 画面は出るのに、何も束縛していなかった

Phase 3.5 のシェル（`app/ui/shell.html`）は、エンジンの `data-m-*` で C++ と繋がる HTML である。
書き上げて描画させると、ツールバーもツリー枠もプロパティ枠もきちんと出た。**そして木も
プロパティも一つも束縛できていなかった。**

- `data-m-text="item.name"` — repeat の中はフィールドを**裸**で書く。`resolve()` は path を
  item から辿るので、`item` という名のフィールドを探して undefined になる
- `data-m-attr="src:item.icon"` — 値を差し込む属性は `{}` が要る。無いと文字列
  `"item.icon"` がそのまま `src` に入る
- プロパティ側の `data-m-repeat` に `<template>` が無く、展開されずに空の行が一つ残る

三つとも、束縛器は**何も言わない**。BINDING.md 自身がその危険を認めて「`mitiru lint` が
静的に照合する」と書いているが、その道具はエンジンに実装が無かった。

なので `tools/shell_audit.py` を書いた。照合する相手は文書ではなく**束縛器の実装**にしてある
（対応属性は `mitiru_bind.js` を読んで取り出す）ので、エンジンが増やせば追随し、落とせば
こちらが落ちる。見るのは 9 点 — 属性の実在、`<template>`、repeat 内の裸 path、`{}`、
行動名が Keymap にあること、`data-m-class` のクラスが CSS にあること、束縛器の読み込み、
アイコンの実在、そして下の順序依存。**9 点すべて、傷を入れて落ちることを確認済み**。

## 第三の駆動系が、揃えたはずの語彙から外れていた

ビューポートとコマンド層は「同じ編集が両方から届く」ことを門にしてある（`keymap_audit`）。
シェルはその**三つ目**の駆動系で、書いた時点ですでにずれていた — `edit.remove` と
`edit.mute`、語彙は `edit.delete` と `edit.toggleMute`。同じ操作に二つ名前がある状態である。

`keymap_audit` にシェルを第三の引数として渡し、**「鍵が届く」ではなく「何かの操作が届く」**を
条件にした。ボタンも到達手段として数える。これは Grasp3D のカメラ選択（Genuine / X / Y /
Z-direction）を移すのに要った — Genuine は Maya にも Blender にも概念が無く、プリセットに
束縛を要求すると**存在しないキーストロークを発明すること**になる。

## Genuine を移したら、Makina 側の穴が見つかった

Grasp3D は対話用カメラを X/Y/Z 方向のビューと別に保持していて、ツールバーから戻れる。
Makina の `lookAlong()` は yaw と pitch を上書きするので、**軸方向を一度覗くと、それまで
時間をかけて決めた画角は戻せなかった**。移植のために元の UI を読んで初めて出てきた欠落で、
`view.genuine` として塞いだ。

検査は絵で 3 枚。`--actions`（鍵ではなく行動名を直接渡す入口。シェルのボタンも同じ道を
通る）で撮り、

- 開始 vs `view.front` — **9.36% の画素が違う**。これが対照で、ここが 0 なら下は
  「何もしていないもの同士が一致した」で通ってしまう
- 開始 vs `view.front` → `view.genuine` — **0 画素**

`view.genuine` を外すと後者は落ちる（確認済み）。

## 直したつもりで、測り方を間違えていた

`viewport-check.bat` に検査を足した直後の 1 回だけ、`call :run` が
**"cannot find the batch label specified"** で死んだ。1 件だけ落ちて残りは走り、最後に
「nothing was saved」というまったく別の見た目の失敗として出た。

改行のせいだと考えた。`grep -q $'\r'` で調べたら .bat が全部 LF に見えたからである。
**この測り方が間違っていた** — この Git Bash の `grep` は CRLF ファイルの CR を見つけない
（`printf 'a\r\nb\r\n'` で作った対照ファイルでも「CR なし」と答える）。Python で
バイトを数えると `viewport-check.bat` は最初から CRLF で、`.gitattributes` にも
`*.bat text eol=crlf` と、この失敗そのものを名指しした注記つきで書いてあった。

つまり**改行は最初から正しく、私の「修正」は 1 バイトも変えていない**。それでも次の実行から
通ったので、直したように見えていた。同じサイズでの書き戻しでも、行を足してサイズを変えても
再現しない。**原因は特定できていない。**

記録しておくのは次の 3 点だけ:

- ラベルが見つからないという .bat のエラーは、一度きりで消えることがある。
  内容を疑う前にもう一度走らせる
- 改行を測るなら Python でバイトを数える。この環境の `grep` は当てにならない
- 作業コピーの .bat 15 本が LF になっていた（過去の編集スクリプトの副作用で、
  `.gitattributes` の指定と食い違っていた）。CRLF に揃えたが、**上の失敗とは無関係**である

「直った」と「直した」は別で、間に何もしていなくても前者だけ起きることがある。

## 13 本登録されていて、7 本しか走っていなかった

`verify-all.bat` が `everything agrees` を出すとき、走っていたのは makina-core の
**13 本のうち 7 本**だった。`camera_check` / `pick_check` / `keymap_check` /
`transform_check` / `selection_check` / `material_check` / `mesh_compare` /
`pov_import_check` の 8 本は `add_test` で登録されているが、**ctest を呼ぶものが無かった**。

`build-and-test.bat` が名指しで動かしているのは、Java のダンプを引数に取る 7 本だけである。
引数の要らないものは `add_test` に任せる設計になっていて、その `add_test` を回収する側が
どこにも無かった。

走らせたら 8 本とも通ったので、**壊れてはいなかった**。壊れていたのは「everything agrees」の
意味のほうで、見かけの半分しか覆っていなかった。第 4 の照合軸（メッシュ書き出し）も、
ピックの検査も、この中に居た。

`build-and-test.bat` に `ctest --no-tests=error` を足して塞いだ。`--no-tests=error` は
「1 本も見つからなかった」を成功にしないためで、ここで学んだのと同じ失敗の再発である。

**通った件数を数えないと、通ったことは何も意味しない。** このプロジェクトで 4 度目になる。

## シェルの検査に、C++ 側を足した

`ViewState.hpp` が「シェルが読んでよい鍵」の語彙で、`shell_audit.py` の J がそれと HTML を
突き合わせる。属性の綴りが正しく repeat の書き方も正しくても、C++ が push しない名前は
同じように黙って何も起こさない。BINDING.md が「静的な照合でやる」と書いて実装されていない
のは、まさにこの部分である。

宣言が願望にならないよう、`viewstate_check.cpp` が JSON を実際に構築して
`publishedItemFields()` と突き合わせる。**語彙を宣言する側と、それを守る側を別々に検査する。**

否定対照は `tools/shell_audit_control.py` に置き、**門と一緒に毎回走る**。写しに傷を入れて
検査するので本物には触らない — 以前は本物を書き換えて戻していたが、途中で落ちれば壊れた
シェルが残る。確かめている当のものより危ない対照だった。12 項目すべて発火する。

## `.*` が行の端まで走って、主張が空になっていた

ビューポート自身が出す状態（`--dump-state`）に 5 つの主張を置いた。そのうち 1 つは
**どんな入力でも通る**主張だった。

    findstr /R "id.:14,.*selected.:false"

ツリーの JSON は 1 行なので、`.*` はノード 14 の終わりを越えて走り、**別のノードの**
`"selected":false` を拾う。ノード 14 を選択しても通り続ける。「選択していないノードに印が
付いていないこと」を確かめているつもりで、何も確かめていなかった。

見つけたのは対照のほうである。13,15 の選択に 14 を足して走らせたら、落ちるはずの行が
黙って通った。`[^{]*` に替えて、ノードの境界で止まるようにして解決。

**主張を書いたら、それが落ちる入力を 1 つ作って走らせる。** 落ちなければ、その主張は
書いてあるだけである。このプロジェクトで 5 度目になる。

## ボタンが効かない、の 4 つの理由

シェルを C++ に繋ぐとき、ツールバーのボタンは 4 回「何もしない」を経験した。**4 回とも
症状は同じ**で、押しても木が変わらない。原因はそのたびに違った。

1. **判定が早すぎた** — 準備完了をロード完了で見ていた。ドキュメントが出来た時点では
   まだ何もラスタライズされておらず、CEF は初回ペイントまで入力を捨てる。初回ペイントで
   判定するよう直した（`paintStats().paintCount > 0`）
2. **移動と押下が同じフレームだった** — ポインタの所有権は押した瞬間に決まるので、
   カーソルが到着したフレームでいきなり押すと、**実マウスの居場所**で判定される。
   最初の試みはそれで、ボタンではなく選択解除が起きた
3. **HTML がプレーンテキストとして配信されていた** — エンジンの `app://` が
   `SetMimeType("text/html; charset=utf-8")` と charset ごと渡していた。CEF は型だけを
   期待するので、Chromium は全体を未知の型として扱う。`<!DOCTYPE html>` から始まる
   ソースが画面に出て、DOM は無い
4. **登録先が違った** — `data-m-action` は `mitiru.dispatch` を通り、
   `state.dispatch|{action,payload}` という**単一の** cefQuery になる。行動名は
   メッセージの**中身**であって名前ではない。`registerHandler("edit.toggleMute", ...)` は
   ページが決して送らないものを待っていた。正しくは `StateStore::onAction`

**4 つとも「押しても何も起きない」としか言わない。** どれか 1 つを直しても症状は変わらない
ので、「直っていない」と「別の理由で止まっている」の区別がつかない。効いたのは推測を
やめて測ったときで、3 点（ツールバー・ツリー・中央）のアルファを出したら
`bar=1 tree=1 mid=0` と返り、当たり判定は正しいと分かった。そこから先は消去法だった。

## ボタンからの経路は、他のどの検査でも通らない

`--keys` はキーマップを通り、`--actions` はページを飛ばす。**どちらも「ツールバーが
何かに繋がっているか」を答えない。** そこだけが Phase 3 の主張そのものなので、
`--click <x,y>` を足した。手と同じポインタ経路に流し込む。

検査は (478,15) のミュートボタンを押す。ミュートなのは delete が `data-m-confirm` を
持っていてモーダルへの二度目のクリックが要るからで、かつ**ノードが木に残る**から --
通った run は「何かが変わり、何も消えていない」run になる。

対照はボタンの外（700,400）を押す版で、落ちることを確認済み。

## 一晩で 4 回、「試したものが古かった」

同じ形の失敗を 4 回した。**どれもビルドは成功と言い、試したものは前の版だった。**

| 何が古かった | どう気づいたか |
|---|---|
| ビルドされなかった実行ファイル | 検査の件数が増えなかった |
| コンパイルされなかったヘッダ | ヘッダを編集した直後に ninja が "no work to do" |
| 実行されなかったテスト | add_test 済み 13 本のうち 7 本しか走っていなかった |
| 配布されなかった HTML | CSS を直して建て直して試して、まだ直っていなかった |

最後のものが一番高くついた。`POST_BUILD` を exe に付けていたので `shell.html` だけを
直してもリンクが走らず、複製も走らない。**アウトライナの行クリックが効かない**という
症状を 1 時間追いかけて、原因を「repeat が生成した要素の側にある」と書いて一度コミット
した。**その診断は誤りだった。** ALL 付きの custom target にして毎回配布するようにしたら、
同じクリックが `selected 11 from the outliner` と答えた。

**「ビルドが通った」は「試したものが新しい」を意味しない。** 4 回とも、確かめる手段は
違った（件数・ninja -t deps・ctest の本数・配布先の中身）が、質問は 1 つだった --
**私がいま動かしているのは、私がいま書いたものか。**

## select.pick だけが沈黙する、ように見えた

行クリックの切り分けはこう進んだ。ツールバーのボタンは効く。行は効かない。行の
`data-m-action` を `edit.undo` に変えると効く。`data-m-arg="id"` を残したままでも効く。
つまり **`select.pick` だけが届いていない**、という結論になりかけた。

実際には配布が古かっただけで、`select.pick` にも `data-m-arg` にも何の問題も無かった。
切り分けは正しく、前提が腐っていた。**二分探索は、両側が同じ版でなければ嘘をつく。**

## 直す前に、計測器を置いた

プロパティ欄に打った数字が届かない件で、疑いは 2 つあった。エンジンの `MitiruCefInput` が
`native_key_code` に生スキャンコードを入れていること（Windows の Chromium は lParam 形式を
期待する）と、Enter に `KEYEVENT_CHAR` が送られていないこと。

**どちらも直さなかった。** 代わりに `app/ui/keyprobe.html` を置いた -- 入力欄 1 つと、
`keydown` / `keypress` / `keyup` / `input` を `console.log` するだけの頁である。コンソールは
stderr に出るようにしてあるので、ヘッドレスの実行から読める。

    PROBE field focus
    PROBE keydown  key=3     code=Digit3 which=51 value=start
    PROBE keypress key=3     code=Digit3 which=51 value=start
    PROBE input                                    value=start3
    PROBE keydown  key=Enter code=Enter which=13   value=start3

**キーの経路は完全に無実だった。** 疑っていた 2 箇所を「直して」いたら、動くものを 2 つ
壊したうえで、症状が消えたのを直った証拠と取り違えていた。

同じ手順でシェル側を測ると `set` が出て、木が実際に変わった。この 2 つの run の差は
ページだけである -- 計測器は原因を教えないが、**どこを見なくてよいかを教える**。

## ページが C++ に届く道は 3 本あり、どれも他の検査では通らない

| 道 | 何を押すか | 検査 |
|---|---|---|
| ボタン | ツールバーのミュート | `button` |
| 行 | アウトライナのノード | `outliner` |
| 欄 | プロパティの数値 + Enter | `field` |

`--keys` はキーマップを通り、`--actions` はページを飛ばす。**3 本とも、専用の入口
(`--click` / `--text`) を作らないと 1 度も踏まれない。** 対照はそれぞれ、ボタンの外を押す /
行の外を押す / 数字でない文字を打つ で、3 つとも落ちることを確認済み。

## 反対向きにも測る

**「2 つのレンダラが一致した」は「どちらも描いていない」でも成立する。**

- 反射: 切ると 1.71% の画素が 40 階調超で動く（最大 68）。入れて POV と平均 3.78
- 影: 板を手前に置くと隠れ、**奥に置くと隠れない**。後者が無いと
  「メッシュが後から描かれるので常に勝つ」実装でも通る
- ビューポートの検査: 5 件のうち 4 件は**わざと壊して落ちるのを確認済み**
- シェルの検査: 12 件**全部**が、傷を入れると落ちる。しかも**毎回**確かめている
- メッシュ照合: 頂点が表面上にあることは**要求しない**（重なるソリッドの列なので
  埋もれた面は深く負が正しい）。要求するのは**外に出ていないこと**だけ

## 走らせ方

```bash
verify-all.bat
```

Java の参照ダンプ生成 → makina-core のテスト → GPU（輪郭・画素・カメラ・焼いた DXIL）
→ ビューポートの操作、の順に走り、最後に `everything agrees` を出す。

POV の側の数値そのものを問い直すときは:

```bash
python spike/pov_filter_probe.py
```

`finish{ambient 1 diffuse 0}` の面は「ピグメント × 係数」がそのまま画素に出るので、
POV に**自分の係数を吐かせる**ことができる。透過の 2 つの取り違えはこれで割れた。

```bash
python spike/pov_camera_probe.py
```

カメラは「方向 → 画素」の写像なので、**既知の方向に光る球を 1 つ置いて、どの画素に出るかを見る**。
`panoramic` はこれで割れた（下記）。

`ctest` は**この 1 リポジトリだけで完結する**ぶんを走らせる（Grasp3D も JDK も GPU も不要）。
Java 参照との比較は `build-and-test.bat` にある — 参照ダンプを毎回作り直すのが、
それが古くならない唯一の担保なので。

# 何をどう確かめているか

**このプロジェクトで一番強い主張は「速い」でも「きれい」でもなく、
**独立に書かれた実装どうしが一致する**ことである。**
自分で書いた 2 つが一致しても、同じ勘違いを共有しているだけかもしれない。

だからこの文書は「テストがある」ではなく **どの軸が何を捕まえ、何を捕まえないか** を書く。

---

## 5 つの照合軸

| 軸 | 何と何 | 規模 | 捕まえるもの |
|---|---|---|---|
| 1 | 移植 ↔ Grasp3D（Java） | 501 + 7,812 件 | 距離場・計測・POV 出力の移植ミス |
| 2 | 距離場 ↔ 境界表現（BSP） | 156,932 サンプル | ブーリアンの解釈違い |
| 3 | 距離場 ↔ POV-Ray（**輪郭**） | IoU 0.9949〜0.9996 | 幾何・変換・カメラ・左右の向き |
| 4 | 距離場 ↔ POV-Ray（**画素**） | 平均差 0.14〜4.76 | 陰影・マテリアル・パターン・光・影・カメラ種別・透過 |
| 5 | 書き出したメッシュ ↔ 距離場 | 最悪 0.0188（許容 0.0762） | 出口の表現が中身とずれていないか |

加えて **POV の往復**（エクスポート → 読み戻し）が全フィクスチャで **差 0.00e+00**。

> **軸 3 と 4 は別物である。** 輪郭はジオメトリだけを見るので、
> **2 つのレンダラが全ての輪郭で一致し、全てのマテリアルで食い違う**ことがありうる。
> 軸 4 はそれを塞ぐために、POV の `finish{}` と `pigment` を**こちらが POV に合わせて**実装して初めて成立した。

## 軸 4 が実際に見つけたもの

比較器（`spike/src/color_compare.cpp`）は作った初回に 2 件を出した。どちらも
**目では分からず、数字にすると一目**という種類である。

**ブーリアン節点のマテリアルがエクスポートされていなかった。**
Grasp3D のファイルはマテリアルを必ずプリミティブに置くので今まで表に出なかった。
レンダラは祖先を辿って解決するので**塗っていて、.pov は塗っていなかった** —
POV 側にチェッカーの箱が丸ごと存在しなかった。平均差 55.4 → 7.7。

**POV のスペキュラは指数ではなくガウシアンだった。**
`exp(-(acos(N·H)/roughness)²)`。Blinn-Phong の指数に変換していたので、
roughness 0.6875 では**ほぼ平坦**になり全画素が持ち上がる。
暗いチェッカーが 100、POV は 76 で、**片方の色だけ一律に**ずれていた。平均差 4.7、penrose は 8.6 → 4.2。

fisheye も初回 mean 95 で外れた。**POV は right/up ベクトルの長さで正規化する**ので、
アスペクトを掛けると「見た目の丸い」絵になり全画素で食い違う。

**透過は 2 つの取り違えが重なっていた。** どちらも「係数を当てて通す」ではなく、
**POV に係数そのものを吐かせて**割った。`finish{ambient 1 diffuse 0}` の球は
画素にピグメントの色 × 係数がそのまま出るので、フィルタと色を振れば係数が読める。

**1つ目 — 減衰は `1 − filter` ではない。** POV は **`1 − filter × ピグメントの最大チャンネル`**
で減衰させる。白では両者が一致するので、色を付けて初めて分かれる。
実測 0.4117 / 0.4115 / 0.4117 に対し `1 − 0.75 × 0.784 = 0.4118`、
filter 0.25 と 0.5 でも小数 4 桁まで合う。
透過側の色付けが `filter × ピグメント` であることも、板を後ろに置いて
**球の表と裏の 2 層**として計算した値（0.3743/0.6513/0.4242）が
実測（0.3763/0.6514/0.4233）に一致することで裏が取れた。

**2つ目 — 距離場の勾配は必ず外を向く。** 透過体の裏の壁は内側から当たるので、
法線が視線から背を向けたまま照明され、影の中にあるかのように落ちていた。
**POV に裏面という概念は無く、見ている側へ法線を倒す**（POV の平面が両側から照らされるのと同じ理由）。

この 2 つで glass は 14.90 → 2.43。さらに**輪郭ぎわだけ**が残ったので見に行くと、
内側は階調まで一致しているのに外周 1〜3 画素で 134 対 66 だった。
擦れる角度では面を離れる一歩が閾値の内側に収まってしまい、
**同じ面が層の数だけ自分の上に重なっていた**。閾値を抜けるまで進めるようにして
glass **0.27**、ペットボトル（アルファ 0.1 の殻が何重にもある）**4.02**。

層の上限は POV の `max_trace_level` と同じ 5 にしてある。16 まで上げても平均は動かなかったので、
**深さではなく式の問題だった**ことがここでも確かめられている。

## 指標を 2 度作り直した

**どちらも「閾値を選べば通る」に逃げなかった結果である。**

**パーセンタイルは硬い縁のパターンで機能しない。**
チェッカーのマス境界では 2 色が 200 階調離れているので、
面の位置が半画素ずれる（片方はマーチ、片方は求解なので必ずずれる）だけで
その画素に 200 が入る。平均 4.7・パターンは完全に一致しているシーンで p99 が 41 になった。
→ **「強く違う画素の割合」**に変えた。

**メッシュの照合は三角形自身の辺長で測ってはいけない。**
24 分割のトーラスを引くと、**削り残る量はトーラス側の分割**で決まるのに
残るスライバは極小なので比が 113 倍に跳ねる。
`hero_flange` の最悪点は場の外 0.0087 で、`1.15 × (1 − cos(π/24)) = 0.0099` に一致した。
**誤差は「削られる面」ではなく「削る面」に属する。** → シーン半径を尺度にした。

## 照合しないと決めたもの

**近似して「読めた／描けた」ことにするのが、この設計で最悪の失敗形である。**
落ちてくれないので誰も気付かない。

| 対象 | 理由 |
|---|---|
| POV のノイズ系 pigment（marble / bozo …） | POV 独自の置換表なしでは「似た何か」にしかならず、照合できない |
| `sor` / `blob` / `isosurface` など | このモデルに対応する形が無い。円錐の積み重ねで近似すると別の立体になる |
| `rand` / `seed` | POV の乱数そのものを再現しない限り一致を主張できない |
| `panoramic` カメラ | POV の縦方向の対応を 2 通り試して 159 と 95（限度 6）。3 通り目は「通るまで当てる」になる |
| 無限平面（軸 3・5） | 半空間はソリッド形を持たない。有限の代用が尽きたところで必ず食い違う |

いずれも**名前を挙げて断る**。`makina_povin` は読めなかった構文を行番号つきで報告し、
`CsgBake` は焼いた .cso がそのシーンから焼かれたものかをハッシュで照合する。

## 反対向きにも測る

**「2 つのレンダラが一致した」は「どちらも描いていない」でも成立する。**

- 反射: 切ると 1.71% の画素が 40 階調超で動く（最大 68）。入れて POV と平均 3.78
- 影: 板を手前に置くと隠れ、**奥に置くと隠れない**。後者が無いと
  「メッシュが後から描かれるので常に勝つ」実装でも通る
- ビューポートの検査: 5 件のうち 4 件は**わざと壊して落ちるのを確認済み**
- メッシュ照合: 頂点が表面上にあることは**要求しない**（重なるソリッドの列なので
  埋もれた面は深く負が正しい）。要求するのは**外に出ていないこと**だけ

## 走らせ方

```bash
verify-all.bat
```

Java の参照ダンプ生成 → makina-core のテスト → GPU（輪郭・画素・カメラ・焼いた DXIL）
→ ビューポートの操作、の順に走り、最後に `everything agrees` を出す。

POV の側の数値そのものを問い直すときは:

```bash
python spike\pov_filter_probe.py
```

`finish{ambient 1 diffuse 0}` の面は「ピグメント × 係数」がそのまま画素に出るので、
POV に**自分の係数を吐かせる**ことができる。透過の 2 つの取り違えはこれで割れた。

`ctest` は**この 1 リポジトリだけで完結する**ぶんを走らせる（Grasp3D も JDK も GPU も不要）。
Java 参照との比較は `build-and-test.bat` にある — 参照ダンプを毎回作り直すのが、
それが古くならない唯一の担保なので。

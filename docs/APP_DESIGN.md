# Makina アプリの設計（Phase 3）

**状態**: 設計済み。§8 の 1〜4 と 6（Camera / Pick / Keymap / ビューポート / 変形）は
実装・テスト済み。残るのは 5（CEF シェル）だけで、これは `external/cef` の取得待ちである。

Phase 3 は工数見積り 6〜9 週で、このプロジェクト最大の山である。
だからこそ**最初に決めておかないと後で戻れないこと**だけをここに書く。
UI の見た目やパネルの配置は書かない — それは作りながら変わるもので、設計ではない。

## 1. 誰が何を持つか

```
   CEF（HTML/CSS/JS）          C++                        GPU
   ─────────────────────       ──────────────────         ─────────
   アウトライナ                History<Scene>  ← 唯一の正
   プロパティ欄                Camera
   ヘッダ（操作の実況）        Selection                  レイマーチ
   メニュー                    Keymap
                               ↑ ↓ StateStore
```

**ツリーの正は C++ の `History` にしかない。** JS はコピーを持たない。
これはエンジンの規約（bridge は signal-only、state ownership は C++）であると同時に、
Makina 固有の理由がある — **入力口が 3 つある**（GUI・CLI・エージェント）。
JS にツリーを持たせた瞬間、CLI から編集したときに JS 側が古くなる。

`makina-core` 側は Phase 7 で既に揃っている：

| 要る機能 | 実装 |
|---|---|
| 編集 | `Edit.hpp`（id 指定・木を作り直す） |
| 履歴 | `History.hpp`（flat POD のスナップショット） |
| コマンド | `Command.hpp`（JSON、名前付きパラメータ、失敗で停止） |

**アプリは新しい編集ロジックを一切書かない。** ブリッジに繋ぐだけである。

## 2. ブリッジの契約

エンジンの `StateStore` にそのまま乗る（`set` / `emit` / `onAction`）。

### C++ → JS（`set`：retained。購読すると直近値が即届く）

| キー | 中身 | いつ変わるか |
|---|---|---|
| `makina.tree` | `writeScene()` の JSON | 編集のたび |
| `makina.selection` | 選択中の id の配列 | 選択のたび |
| `makina.history` | `{labels: [...], at: n}` | 編集・undo・redo |
| `makina.camera` | `{eye, target, fovY, ortho}` | カメラ操作のたび（間引く） |
| `makina.keymap` | 現在のキーマップ（表示用） | プリセット切替時 |

### C++ → JS（`emit`：一回限り）

| イベント | 中身 |
|---|---|
| `makina.op` | ドラッグ中の操作の実況（`{op:"move", axis:"x", value:5.0}`） |
| `makina.error` | 拒否されたコマンドの理由 |

### JS → C++（`onAction`）

| アクション | 中身 |
|---|---|
| `makina.command` | **`Command.hpp` の JSON をそのまま**。追加・削除・付け替え・set・rename・material・undo・redo |
| `makina.select` | `{ids: [...], mode: "replace"｜"add"｜"toggle"}` |
| `makina.view` | `{fit: "selection"｜"all"}` / `{look: "front"｜"right"｜"top"}` / `{ortho: true}` |
| `makina.keymapPreset` | `{preset: "maya"｜"blender"}` |

> **`makina.command` が 1 本しかないのが要点である。** GUI のボタンも、CLI も、
> エージェントも、**同じコマンド JSON を投げる**。
> 3 つの入力口が同じツリーを触るという Phase 3 の目的が、追加の実装なしで満たされる。
> 増やしたくなったら、まず「`Command.hpp` に足りない動詞は何か」を先に問うこと。

## 3. 入力の分割 — ビューポートは CEF を通さない

**パネルは CEF、ビューポートはネイティブ。**

CEF オーバーレイは HTML の当たり判定を持つ領域だけがイベントを取り、
それ以外はそのまま C++ の入力に落ちる。

**なぜ分けるか。** オービットとパンは 1 フレームでも遅れると露骨に分かる操作である。
マウス移動を `cefQuery` で往復させると、JS → IPC → C++ → 描画 の経路になり、
**このプロジェクトで唯一「体感」が問題になる箇所に、最も長い経路を通すことになる**。

パネル側は逆で、ボタンを押してからツリーが更新されるまでに 1 フレーム余分にかかっても誰も気付かない。

| 領域 | 入力経路 | 理由 |
|---|---|---|
| ビューポート | Win32 → C++ | 遅延が体感に直結する |
| アウトライナ / プロパティ / メニュー | CEF | 遅延が問題にならない。HTML で書けることの利点が勝つ |

## 4. Undo は履歴でやる。エンジンの巻き戻しではない

**PLAN.md の当初の方針（「Undo/Redo は実装しない。エンジンの巻き戻しに委譲する」）を変更する。**

エンジンの巻き戻しは **1 フレーム単位**の ring である。モデラーの Undo が欲しいのは
**1 編集単位**で、しかも「何を取り消すのか」がラベルで見えなければならない。

- 溝の半径をドラッグで 2 秒動かしたら、それはフレーム換算で 120 ステップ、編集としては 1 つ
- 300 フレーム巻き戻すのは「直前のブーリアンを取り消す」ではない

`History.hpp` は既にあり、スナップショットは flat POD のコピーなので、
**コマンドに逆操作を持たせる必要が無い**（逆操作が微妙に間違っている、という事故が起きない）。
コストは 1 ステップ約 26 KB で、100 ステップでも 3 MB を下回る。

**エンジンの ring は残す。** 用途が違う — あちらはタイムトラベル inspector（軸 2）で、
「アプリ全体が毎フレームどうだったか」を見るためのものである。両立する。

## 5. 選択（ピッキング）は距離場を 1 本撃つだけ

ID バッファも読み戻しも要らない。

1. カーソル方向にレイを 1 本、**描画と同じ距離場**をスフィアトレースする（`CsgSolid::raycast` と同じ）
2. 当たった点に**最も近いプリミティブ**を探す（`Measure.hpp` の `GapResult::fromPrim` と同じ仕組み）
3. そのノードの id を返す

**メッシュだと ID バッファを描いて GPU から読み戻すところ**が、ここでは CPU のレイ 1 本で済む。
クリック 1 回あたり数ミリ秒で、毎フレームやる必要が無い。

絵とアタリが同じ定義から出るので、**見えているのに選べない / 見えていないのに選べる**が構造的に起きない。

> ⚠ 返すのは「当たったプリミティブ」であって「ユーザーが選びたい塊」ではない。
> ブーリアンの中の刃を掴んでしまう。**既定では最も外側のブーリアンを選び、
> `Alt`+クリックで 1 段ずつ内側に降りる**（Maya の hierarchy 選択と同じ考え方）。

## 6. カメラ — ここが体感を決める

PLAN.md が名指ししている 2 つ（Grasp3D の `dca118a` がまさにこの修正だった）：

1. **オービットは選択物を軸に回る。** ワールド原点ではない。
   軸が視界の外にあると、回した瞬間に対象が画面から消える
2. **パンの移動量は視距離に比例する。** 定数だと、寄っているときは飛びすぎ、
   引いているときは動かない

どちらも**純粋な算術**である。CEF もウィンドウも要らない。
だから**ここだけは先に、ヘッドレスで、テスト付きで実装する**。
UI を作ってから触って直す、という順序にすると「なんとなく気持ち悪い」を数字で詰められなくなる。

フィット（`F` / `A`）も同じ — 対象の AABB（`Bounds.hpp` に既にある）から
距離を決めるだけで、これもヘッドレスで検査できる。

## 7. キーマップはデータ

`keymap.json` を C++ が読み、`makina.keymap` で JS に push（表示用）。
Maya / Blender の 2 プリセットを同梱する。

コードに直接キーを書かない理由は、完了条件に
「Maya か Blender の経験者に触ってもらい、迷わず動かせたことを確認」があるから。
**触ってもらった結果を反映するのに再ビルドが要る形だと、その場で試せない。**

## 8. 作る順序

CEF の取得（`external/cef`、数百 MB）が済んでいないので、**要らないものから作る**。
これは待ちを避けるための都合ではなく、§6 の理由でどのみち先にやるべき順序である。

| 順 | 何を | CEF | 状態 |
|---|---|---|---|
| 1 | `Camera.hpp` — オービット / パン / ドリー / フィット / 軸ビュー / 平行投影 | 不要 | ✅ 36 checks |
| 2 | `Pick.hpp` — レイ 1 本 → ノード id、外側のブーリアンへ昇る | 不要 | ✅ 17 checks |
| 3 | `Keymap.hpp` — JSON → 束縛、2 プリセット | 不要 | ✅ 39 checks |
| 4 | ビューポート単体（Win32 + DX12、HTML 無し） | 不要 | ✅ `app/viewport` |
| 5 | CEF シェル、アウトライナ、プロパティ | **要** | 未（CEF 未取得） |
| 6 | 変形（移動・回転・拡縮）と数値直接入力 | 不要 | ✅ 66 checks + `app\viewport-check.bat` |

6 は「CEF が要る」と見積もっていたが、要らなかった。
**数値を打つのに HTML の入力欄は要らない** — 打鍵はビューポートに届いており、
ヘッダの表示は `TransformSession::status()` が文字列で返す。
CEF が要るのはその文字列を**どこに出すか**だけで、それは 5 の話である。

### ドラッグ中は生成シェーダを使わない

生成 → DXC → PSO は 150〜250 ms かかる。**編集 1 回なら払える。毎フレームは無理である。**
そこで**変形中だけインタプリタ経路に切り替える**（`scene_interpret.hlsl`）。
木がバッファで届くのでコンパイルが要らず、**シーンに依らないので PSO は起動時に 1 つ作れば足りる**。
確定した瞬間に生成シェーダに戻る。

インタプリタは 5.6〜11.4 倍遅い（`docs/SPIKE_PERF.md`）が、ここではそれが正しい取引である
— **数倍重いフレームは「今」出る。シェーダのコンパイルはドラッグが終わるまで出ない。**

プレビューは `applyTransform` を**履歴ではなく複製に**当てて作る。
だから取り消しは何も戻す必要がない — 一度も確定していないからである。

**1〜3 で分かったこと**（設計時には見えていなかった）:

- **パンはアスペクトを持たないと成立しない。** 横方向の移動量は縦の `aspect` 倍で、
  落とすと 16:9 で横だけ 1.78 倍遅れる。実測で 9 ケース中 6 ケースが落ちた
- **穴の内壁は真上からは選べない。** 壁が縦でレイも縦なら交わらない。
  「穴をクリックする」は「穴に向かって撃つ」ではない
- **束縛には文脈が要る。** Blender の `X` は通常 delete、変形中は X 軸拘束。
  同じキーの別モードなので、文脈が無いと片方が到達不能になる
- **入力は「押されている」と「今フレーム押された」を分ける必要がある。**
  オービットは前者、ショートカットは後者。取り違えると毎フレーム発火するショートカットになる
- **ウィンドウの外へ出たドラッグも届かせる**（`SetCapture`）。でないとオービット中に固まる
- **`NOMINMAX` はビルド定義に置く。** `d3d12.h` も `windows.h` を引くので、
  片方のヘッダに書くと「include 順のルール」になってしまう

**1〜4 と 6 で「触って回せて選べて動かせる」ところまで来た。** HTML が要るのは 5 からである。

GUI は自動では見られないので、ビューポートには `--frames N` と `--screenshot <path>` がある。
**「ビルドが通って落ちなかった」は描けている証拠にならない**ので、絵を出させて確かめる。

変形はさらに検査が要る。**絵が変わったことは「意図した通りに変わった」ではない**ので、
`--keys "W Y 3 ENTER"`（1 フレーム 1 打鍵、実物と同じ順序）で状態機械を回し、
`--save` で木を書き出して**基準ファイルとバイト比較**する。
値の照合ではなく同一性の照合にしてあるのは、「6.0987 がファイルにある」は
**何も取り消さなかった undo でも成立してしまう**からである。

`app\viewport-check.bat` が 10 件を見る — 移動 / 取り消し / undo / redo /
変形を持たないノードの包み込み / 削除 / 複製 / 削除の undo / **ドラッグ中のプレビュー**。
4 つは**わざと壊して落ちるのを確認済み**である
（Escape の取りこぼし・undo 無効化・redo 無効化・プレビューの木の取り違え）。

**検査そのものが 1 度だけ落ちて次で通った**。放置できないので追ったところ、
`GetKeyState` は**マシン全体の物理キー**を見るので、
検査の実行中にたまたま Shift が押されていると `CTRL+Y` が束縛に一致せず、
redo が黙って起きなかった。`--keys` を渡した実行では物理キーボードを一切読まないようにした。

**プレビューで見つかった不具合**: 絵は仮の木から描いていたのに、
**接地面の高さ・シーン半径・選択ハイライトの箱は確定済みの木から取っていた**。
その結果、確定した瞬間に絵が跳ねた（20,182 画素が変化）。
1 フレームがシーンから引き出すものは**すべて同じ木から**引かなければならない。
直したあとはプレビューと確定後の絵が**バイト単位で一致**する。

なお**インタプリタと生成シェーダ自体は完全に一致している**
（`render_scene --interpret` との比較で差分 0 画素）。
先に絵を見て「インタプリタがずれている」と決めつけていたら、間違った場所を直していた。

複製は `Edit.hpp` に無かったので足した。要点は **id の振り直し**で、
部分木をそのまま複製すると**同じ id のノードが 2 つ**になり、
`Command.hpp` は id でしか対象を指せないので**片方が永久に届かなくなる**。
これも renumber を外して落ちることを確認してある。

**そこで見つかった実際の不具合**: Escape が変形を取り消したあと、
**同じ Escape がキーループに落ちてアプリごと終了していた**。
変形が走っていたかをフレーム先頭で憶えておく形に直した。
モーダルな入力は「消費したキーを後段に渡さない」ことまで書いて初めて成立する。
